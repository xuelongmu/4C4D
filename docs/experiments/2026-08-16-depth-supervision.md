# Depth supervision from MASt3R (issue #19)

Date: 2026-08-16

Tests whether a scale-invariant depth loss against a MASt3R prior closes the
sparse-view generalization gap on the 8-camera split (held out: 4, 6). Baseline
for both seeds is `ab8-staticfreeze`, the production profile at the top of the
enhancement stack: `--max_num_pts 1000000 --gpu_cache --freeze_static_temporal`,
`--res 2`, 7500 iterations. Depth rows add `--depth_supervision` at the default
`--lambda_depth 0.05 --depth_patch_size 32 --depth_alpha_threshold 0.5`.

## The prior

One static depth prior per training camera, generated by
`scripts/make_mast3r_depth_priors.py`:

1. Reduce each camera's 150 frames to a temporal-median background plate.
2. Mark every pixel the subject ever occupies as invalid (temporal MAD > 6/255,
   dilated 9 px). One static prior is then valid at *every* frame of that
   camera, because the pixels where it would be wrong carry no supervision.
3. MASt3R multi-view inference over the 8 plates (complete pair graph, 56 pairs)
   plus global alignment.

Result: 38–64% of pixels valid per camera, 8.2 MB total, stored outside git at
`data/Xuelong/clip_f300_5s_rgb_posefix/depth_priors/` with a provenance
manifest.

**Prior quality: Spearman 0.995, Pearson 0.994** against the RGB bundle-adjusted
triangulation (`scripts/validate_depth_priors.py`). The prior is essentially
exact on reliable points — which matters for reading the result below: this was
not a weak prior that failed to help, it was a near-perfect one.

> **Second trap, in the reference this time.** Scored against *all* triangulated
> points the same prior reads 0.78, and it is the reference that is wrong.
> COLMAP's 2-view tracks are its minimum and are badly unreliable here: measured
> against the recorded Kinect depth their gross-error (>50 cm) rate is 20.2%,
> versus 3.0% at three views, 0.4% at four and 0.0% at five or more. Two fully
> independent priors — MASt3R and the Kinect sensor — disagree with the *same*
> points, which is what identifies the reference rather than the priors as the
> faulty side. `--min_track 3` (default) drops them.

> **Trap, documented so nobody repeats it.** Scoring the prior against
> `sparse/0/points3D` reports Spearman −0.03 and looks like total failure. That
> file is the *training initialization*: 75k synthetic "calibrated rig volume"
> points with empty TRACK entries, whose keypoint associations in `images.txt`
> are placeholders — some project behind the camera. The real triangulation is
> `rgb_init/refined` (3690 points, 9448 observations). The validator now prints
> a reprojection control (0.5–0.8 px on the correct model, ~850 px on the wrong
> one) so this failure announces itself.

## Verdict

**Not adopted.** Control mean 20.38, depth mean 19.52. One depth run landed at
parity (−0.02) and the other 1.69 dB down; neither improved on its control. The
flag ships off by default.

**On what this does and does not establish.** Run-to-run sigma on this scene is
~0.45 dB and training is nondeterministic regardless of seed, so two runs per
arm resolve roughly a 1.5 dB effect — enough to rule out the +1–2 dB the
few-shot literature reports, not enough to pin the true magnitude of the
regression. The two depth runs had near-identical training curves (depth loss,
L1 and point count all track within a percent), so the 1.7 dB spread between
them is not attributable to the depth term doing something different; it is the
process's own variance, on the heavy side. What is solid: **no gain on either
run**, and the mechanism below, which does not depend on PSNR at all.

The seed-42 run also degraded late — its best checkpoint (iteration 4500) scores
20.39, versus 18.65 at 7000 — which neither the 12-image train metric nor the
3-image test metric surfaced.

## Why: the prior had nothing left to add

The depth loss is logged to TensorBoard as `train_loss_patches/depth_loss`. On
seed 43 it starts at **0.082 at iteration 100** and converges to **0.019** —
one minus a correlation, so this is not a small residual on a large scale:
i.e. rendered depth already correlates with the MASt3R prior at 0.92 within the
first 100 iterations, and at 0.98 by the end.

That is not a vacuous metric. Scoring deliberately wrong depth maps against the
same priors at the same patch size:

| "reconstruction" | patch 32 | patch 128 |
|---|---:|---:|
| shuffled noise | 1.000 | 1.000 |
| best-fit plane | 0.383 | 0.372 |
| pure x-ramp | 0.301 | 0.291 |
| **trained model** | **0.019** | — |

A plane scores 20× worse than the trained model, so the loss does discriminate
geometry. The model simply already satisfies it.

This is the load-bearing evidence, and unlike the PSNR table it does not depend
on a noisy estimator: a near-perfect prior (Spearman 0.995) was applied, the
loss it defines was driven to 0.019, and held-out quality did not improve.

**Conclusion: depth ordering is not this scene's binding constraint.** The
calibrated rig gives accurate poses and a volume initialization, so coarse
geometry is right almost immediately. The held-out gap comes from something
else — and notably not from the region the prior covers: the prior is static
structure only, so the moving subject, which is most of the image content and
where held-out error concentrates, receives no supervision at all by
construction.

## Follow-up: per-frame depth for the subject

The static prior excludes the subject, so the obvious next question is whether
depth supervision helps on the pixels it skips. The capture already answers the
hardest part: each Azure Kinect wrote a 640x576 uint16 millimetre depth frame at
30 fps beside the colour video, and `conversion_manifest.json` records
`recordedDepthFramesRead: false` — **it has never been used.**

`scripts/make_depthkit_depth_priors.py` registers it into the colour camera,
reusing `preprocessing/depthkit/convert_depthkit_to_4c4d.py` (the module that
built this scene's COLMAP model) so the conventions cannot drift. The stored
value is z in the colour camera frame, in metres, on the reconstruction's own
scale — the exact quantity the rasterizer accumulates.

| | MASt3R static | Depthkit per-frame |
|---|---:|---:|
| Spearman vs triangulation | 0.995 | 0.979 |
| median absolute error | n/a (arbitrary scale) | **16 mm** |
| coverage of *dynamic* pixels | 0% by construction | **78%** |
| files | 8 | 1200 (232 MB) |

16 mm median error against an independent reference is the registration
validating itself end to end — extrinsics, distortion, scale and frame
convention all correct.

**Not yet A/B'd, deliberately.** At ~0.45 dB run-to-run sigma, detecting a 1 dB
effect needs about 4 runs per arm and 0.5 dB needs ~13; a 2-run A/B like the one
above would only be able to report "no 1.5 dB effect", which is not worth ~5
GPU-hours to learn. The priors and tooling are in place for a properly powered
run when that is worth spending.

## Other recommendations

1. Do not re-test static multi-view depth on rigs with calibrated poses and a
   volume initialization; the measurement above says the signal is already
   there.
2. The flag ships off by default, as `--color_affine` did for the same reason:
   the implementation is validated and cheap to enable for a rig whose
   initialization is worse than this one's.
